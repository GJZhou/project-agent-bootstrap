# 项目管理与提交规则

## 文档位置

- 纯文档默认放在项目根目录 `docs/`。
- 与代码、脚本或其他交付物配套的说明可以放在配套目录，但先向用户确认。
- 首次创建 `docs/` 时创建 `docs/文档清单.md`，并在 `.gitignore` 中加入整个 `docs/`。
- `docs/文档清单.md` 只自动维护托管标记内的清单，用户补充内容放在标记外。

## 规则文件

根目录创建并维护：

- `AGENTS.md`：Agent 工作规则，按托管标记刷新。
- `progress.md`：版本配置和进度记录，保留顶部手动配置项。

两者都写入 `.gitignore`。如果项目没有 `.gitignore`，创建它；如果已有内容，只追加缺失规则，不改动其他规则。忽略规则不影响文件内容更新。

## 外部关联目录

- 父项目的 `AGENTS.md` 只登记外部目录，不默认修改外部目录。
- 父项目运行时，对已登记或用户明确提供的外部目录进行受限分析：目录存在性、根级规则文件、README/构建元数据、一级结构、`docs/`、`progress.md` 和 `.gitignore`。
- 外部目录有唯一规则文件时，外部规则优先；没有规则文件时，编辑外部目录继承父项目规则。
- 外部目录没有规则文件时，不因单次代码编辑强制创建 `AGENTS.md`；只有用户明确要求初始化外部项目规则时才创建。
- 外部目录的文档、进度和 Git 变更在外部目录内独立维护，不写入父项目同名文件。
- 父项目和外部目录同时变更时，按项目根目录分组处理，避免跨目录混合提交。

## 代码设计原则

- 在满足需求和正确性的前提下保持实现直接，避免过度思考和过度防御设计。
- 修改已有模块时坚持最小修改，不重构无关代码。
- 只运行与当前改动相关的必要测试和验证。
- 尽量不改公共接口；确需修改时先分析调用方兼容性，牵连其他模块时向用户报告并确认。

## 变更类型

每个非文档变更批次选择一种提交类型：

- `ADD`：新增功能、首次创建功能模块或首次增加项目能力。
- `MOD`：已有功能的迭代、调整、修复或行为变化。

同一批次同时包含新增和已有功能调整时统一使用 `MOD`。不把 `ADD/MOD` 原样写入消息，而是选择其中一个。
